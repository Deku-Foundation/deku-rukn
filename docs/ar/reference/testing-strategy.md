# استراتيجية الاختبار والتوافق

**الحالة: خطة هندسية.** تمثل اختبارات الوحدات وفحوص CI الحالية نقطة البداية. أما fuzzing ومجموعة التوافق المعيارية واختبارات الأداء المانعة للتراجع فهي أعمال مستقبلية إلى أن تُنفّذ وتعمل ضمن CI.

## طبقات الاختبار

| الطبقة | ما ينبغي التحقق منه | أمثلة |
| --- | --- | --- |
| المحلل المعجمي | أنواع الرموز وتطبيع الأرقام ومواقع المصدر والمحارف غير المدعومة | الفاصلة المنقوطة العربية واللاتينية، مجموعات الأرقام، النص غير المغلق |
| المحلل النحوي | أولوية العمليات والتلازم والمنهيات وعمق التداخل | `2 + 3 * 4`، قوس إغلاق مفقود، تعبير متداخل بعمق |
| المقيّم | دلالات القيم وحالات الفشل | جمع نوعين مختلفين، اسم غير معرّف، القسمة على الصفر، نتائج عددية غير منتهية |
| واجهة الأوامر | قراءة الملف وstdout وstderr ورموز الخروج | مسار مفقود، وسائط متعددة، ملف ليس UTF-8 صالحًا |
| التوثيق | صلاحية الروابط ودقة الأمثلة | بناء اللغات الثلاث ومطابقة المثال البارز مع ناتج CI |
| الإصدار | فحوص قابلة للتكرار وملاحظات التوافق | اعتماديات مقفلة ومراجعة المسودة وقائمة الإصدار |

## ثوابت يجب اختبارها

- كل مصدر UTF-8 محدود الحجم يجب أن ينتهي بنتيجة أو تشخيص لغوي، لا بانهيار غير متوقع للمفسر.
- تعطي الأخطاء المعجمية والنحوية مواقع مفيدة وثابتة.
- لا يغيّر تطبيع الأرقام قيمة العدد المكتوب بأي مجموعة أرقام مدعومة.
- تتطابق أولوية العمليات مع المواصفات وتغطيها اختبارات بعمليات مختلطة.
- ينتج عن الحساب غير الصالح تشخيص بدل قيمة لا نهائية أو NaN صامتة.
- ترفض حدود المصدر والرموز وعمق التحليل المدخلات الكبيرة بصورة متوقعة.
- إما أن تأتي أمثلة التوثيق من ملف حقيقي، أو أن تُوسم صراحة بأنها توضيحية.

من الخطوات المفيدة إنشاء مجموعة ملفات مصدر معيارية تقترن بمخرجات stdout المتوقعة وفئة الخطأ ورمز الخروج. ويمكن أن تستفيد منها لاحقًا تطبيقات المفسر والمترجم البديلة.

## خطة fuzzing

يوفر مشروع [cargo-fuzz](https://github.com/rust-fuzz/cargo-fuzz) وكتاب [Rust Fuzz Book](https://rust-fuzz.github.io/book/cargo-fuzz.html) مسارًا لاختبار شيفرة Rust باستخدام libFuzzer. يجب أن يستدعي هدف fuzzing مستقبلي واجهة التحليل أو التشغيل العامة باستخدام مدخلات UTF-8 عشوائية، مع التحقق من عدم حدوث انهيار أو تعليق أو تجاوز لحدود الموارد.

تقسيم مقترح:

1. هدف للمحلل المعجمي ومدخلات Unicode والبايتات العشوائية.
2. هدف للمحلل النحوي والتداخل العميق والأقواس الناقصة.
3. هدف شامل يستدعي واجهة المفسر ويقبل التشخيصات المنظمة بوصفها نتائج صحيحة.
4. تحويل كل انهيار مصغّر أو نتيجة خاطئة إلى اختبار دائم.

لم يُعتمد fuzzing كميزة مكتملة بعد. يحتاج إلى أداة اختبار تُراجع بصورة مستقلة وبذور قابلة لإعادة الإنتاج وتشغيل آلي قبل وصفه بأنه تغطية نشطة في CI. يتطلب `cargo-fuzz` إصدار Rust الليلي وأدوات sanitizer مدعومة؛ ويمكن أن يبدأ كسير عمل اختياري منفصل.

## القياس وأبحاث المترجم

يجب تأجيل قرارات الأداء حتى تستقر دلالات اللغة وتتوافر برامج ممثلة. قِس التحليل المعجمي والنحوي والتنفيذ وزمن البدء والذاكرة والمدخلات المليئة بالأخطاء كلًّا على حدة. ولا تقارن المفسر الشجري بآلة بايت كود أو مترجم أصلي إلا بوجود مجموعة توافق مشتركة، وإلا فقد تعني السرعة أن أحد التنفيذين ينفذ عملًا أقل.

يجب نشر أمثلة القياس والبيئة وإصدار الأدوات وشرط الصحة والأوامر اللازمة لإعادة التجربة.

## الفحوص المتاحة في المستودع

من جذر المستودع:

```sh
cargo fmt --all -- --check
cargo test --locked
cargo clippy --all-targets --all-features --locked -- -D warnings
cargo run --locked -- examples/hello.rukn
```

لبناء موقع VitePress من مجلد `docs/`:

```sh
npm ci
npm run build
```
